# 藥單血壓當日暫停條件

狀態：2026-10-10 已實作於功能分支，待 PR 審查與 staging 驗證；尚未發布。本文的數值與讀數都是虛構示例。

實作追蹤：[issue #1258](https://github.com/demo-xq7/jia-jian-log/issues/1258)。以 PR 審查與驗證結果為交付依據。

## 為什麼做與醫囑邊界

使用者已明確補充醫囑語意：醫師原本要求持續吃這顆藥；如果今天的血壓低於指定值，今天整天暫停這顆藥；明天重新量測，未達暫停條件時照原藥單繼續服用。這不是只跳過某一劑，也不是永久停藥。照護者需要在藥旁看到這個持續有效的條件，並留下每一天暫停的原因；單純寫在自由備註裡容易漏看。

這是**轉錄已確認的醫囑**，不是系統根據藥名、血壓等級或 AI 產生停藥建議。100 mmHg 只是使用者提出的示例，不是預設值或通用停藥標準。AHA 的居家量測說明要求先與醫療人員確認，不應依居家讀值自行停藥：[Home Blood Pressure Monitoring](https://www.heart.org/en/health-topics/high-blood-pressure/understanding-blood-pressure-readings/monitoring-your-blood-pressure-at-home)。

## 第一版產品範圍

- 在固定用藥新增一個選用的「血壓暫停條件」；未設定的藥維持目前流程。
- 每位病人的每顆固定藥最多一個當日暫停條件：收縮壓（高壓）或舒張壓（低壓）、比較方式、數值、mmHg。100 對應哪一項需依醫囑登錄，不能自行假設。
- 比較方式明列「低於 `<`」「低於或等於 `≤`」「高於 `>`」「高於或等於 `≥`」，不可把包含等號藏在實作裡。
- 由具備該病人 `can_manage_medication` 的照護者填入醫囑日期、依據／原文摘要、生效時間與服藥前量測有效期限；期限無系統猜測的醫療預設值。未確認期限與依據時只能留草稿，不啟用自動比對。
- 同一顆藥有早／中／晚多筆 plan 時，當日暫停涵蓋這顆藥所有尚未服用的固定劑次，畫面列出受影響時段。今天早上已實際服用的紀錄保留，不改成暫停。新增時段也必須受到同顆藥的當日條件約束。
- 第一版不做 AND／OR、多重上下界、心跳／血糖條件、PRN 條件或推播；PRN 仍沿用現有獨立使用事件流程。

## 介面放在哪裡

1. **排藥／編輯藥品**：劑量、時段下方新增可展開區塊「當日暫停條件（依醫囑）」。條件編輯不放進唯讀藥品詳情。
2. **每週藥單、藥品詳情、排藥清單**：藥名與劑量下方一直顯示條件摘要，如「依醫囑：當天收縮壓低於 100 mmHg，當天暫停；隔天重新量測，未達暫停條件時依原藥單服用」。沒有管理權的人也看得到。
3. **服藥打卡、今天頁服藥入口**：同一個共用判斷結果與提示元件，所有入口都必須經過條件確認，不能在首頁另留一鍵繞過。
4. **交接手冊**：列印條件與醫囑生效資訊，明列是已登錄的指示，不在紙上依最後一筆血壓推論現在該不該吃。

手機示意（虛構藥品 A；只有條件已被確認時才出現）：

```text
藥品 A　早餐後 1 顆
依醫囑：當天收縮壓低於 100 mmHg，當天不服用
隔天重新量測，未達暫停條件時照原藥單服用

今日確認血壓：96 / 65 mmHg · 今天 07:50
符合已登錄的當日暫停條件
[記錄今天暫停此藥]
```

## 比對與資料不足

<!-- 為什麼：用昨天或另一位病人的「最新讀數」判斷本次用藥，會產生看起來有根據的錯誤指示。 -->

只讀目前已授權 `patient_id` 的量測，按 `measured_at`（不是上傳時間）列出最近候選；照護者確認本次使用哪一筆。不可默默選某次複測、平均值或較有利的讀數，也不可跳過較新的量測來避開條件。顯示完整高／低壓、量測時間與距今時間；有效期限採已登錄的醫囑設定，不以「同一照護日」代替。

| 狀況 | 顯示與操作 |
| --- | --- |
| 今天符合條件 | 「符合已登錄的當日暫停條件」，主操作為「記錄今天暫停此藥」；確認後原子記錄當日決定，適用期間內禁止正常給藥記錄；只有確定日期被完整涵蓋的未服固定劑次列為已處理，不永久停用 plan |
| 今天未符合條件、也沒有已確認的當日暫停 | 「今日血壓未達已登錄的暫停條件，依原藥單服用」，可進行正常服藥記錄；不可把僅未低於門檻稱為血壓正常或安全 |
| 今天已確認整日暫停，後來再量未低於門檻 | 維持「今天依醫囑暫停」；不能因新讀值自行恢復當天後續劑次，需依醫師新指示走明確更正 |
| 隔天 | 昨天的暫停不沿用，回到「今日待確認血壓」；量測未達暫停條件則回到原藥單，仍達條件則重新確認今天暫停 |
| 今天未量、超過期限、未來時間、只有未同步讀數 | 「尚無可用的今日血壓，請先量測／同步」，不沿用昨天正常值自動恢復 |
| 血壓／條件載入失敗、版本變更 | 顯示「無法確認條件」或「條件已更新，請重新確認」，保留未處理狀態，不能當作沒有條件 |
| 條件尚未生效或已撤銷 | 顯示現行版本；歷史紀錄保留當時版本，不用新門檻重算過去 |

紀錄事實與給藥提示分開：若病人已實際服用，即使條件符合或資料不足，也必須能從次要入口「補記已實際服用」填寫原因、實際時間與確認內容。此入口要求 `can_record`，不授予修改醫囑權限，不得偽裝成系統允許給藥；歷史標示「實際服用紀錄／與條件不符或未完成確認」。

沒有有效量測不等於依醫囑應暫停，不能因此自動產生「今天暫停」。資料不足時可先量測或依醫囑聯絡確認；待確認仍屬未處理。跨到隔天只是結束昨天暫停的適用範圍，不是自動記錄明天已服用或判定血壓正常。

血壓本身的異常判讀與現有聯絡／複測提示照原規格保留；本功能的藥品門檻不修改九級血壓標準、危險值守衛或通知規則。

## 「今天暫停、隔天重新確認」的紀錄語意

- 劑次識別沿用 `(patient_id, plan_id, care_date, dose_number)`；`care_date` 依台北 04:00 照護日，另存實際決定時間。
- 當日暫停另存明確 `rule_day` 與適用起迄時間。使用者說的「今天／明天」按台北日曆日期規劃，不讓現有 04:00 的打卡分組靜默改變醫囑範圍；凌晨劑次可能屬於前一個 `care_date`，但暫停判斷必須依本次給藥日期套用 `rule_day`。設定時明確填入醫囑日界與跨午夜時段，畫面列出「適用日期」；若醫囑有不同日界，需明確登錄而非猜測。
- 顯示四種狀態：尚未處理、待確認今日血壓、已記錄服用、今天依醫囑暫停。只有已實際記錄服用或已確認覆蓋的暫停劑次是已處理，待確認不是完成。
- 保存條件版本及快照、所選血壓的 ID／數值／量測時間快照、決定時間、操作者、原因及實際服用例外的確認內容。
- 暫停不建立假的 `taken_at`、不列入實際服用次數；進度呈現「已服用 X 劑／依醫囑暫停 Y 劑」，全數處理後只能說「本時段已處理完成」。
- 今天頁、近期趨勢、漏服觀察、報告都須區分暫停與未回報；暫停不能被當作漏服，沒有回報也不能假定已暫停。
- 更正保留原決定與原因；當天恢復需登錄新醫囑／更正原因，不能只撤掉某一劑來繞過整日暫停；已實際服用仍可如實補記，同一劑不能同時顯示服用與暫停。
- 今天的暫停不延續到明天；原藥單與醫師的長期血壓條件持續存在。每個新日重新確認，未達條件時沿用原劑量／時段，不需重新啟用藥品或重建藥單。

## 資料契約與設計決定

`medication_hold_rules` 是病人＋藥品的不可變版本，`medication_hold_events` 是 `hold`／`release`／`taken`／`correction` 的不可變事件帳本。`medication_intake_logs` 仍只代表實際服用，新增 `hold_event_id` 連結受控確認。新建藥品須先建立固定計畫，再從排藥編輯條件；所有醫療欄位初始留白。

**日期投影限制**：目前 plan 只有餐前後／睡前等時段，沒有精確服用鐘點，因此不能把「醫囑日與照護日有交集」當成整頁劑次都適用。只有 hold 原始 `[starts_at, ends_at)` 完整涵蓋頁面照護日 `[04:00, 次日04:00)`，才自動計入 held／已處理；實際 intake 永遠優先，待同步事實也不轉為 held。午夜或 18:00 等日界未完整涵蓋時，卡片仍明示整顆藥暫停的精確起訖、禁止正常給藥，並以三語解釋劑次未自動列為已處理不表示可以給藥。不得猜測早餐、晚餐或跨午夜睡前的時刻，也不以單純 `rule_day === care_date` 替代。這是現有資料模型的保守呈現限制，不縮短資料庫的暫停效力。

不另存每劑 `held` 複本：同藥的固定劑次從有效 hold 與真實 intake 即時推導；實際服用優先，新增時段自然繼承，避免投影表漂移。此方案替代原提案的 daily／dose 三表設計。暫停不改 `active`、不新增假的服用時間，沒有填寫條件的藥維持既有流程。

- `medication_hold_context` 依伺服器時間讀取目前生效的最新登錄版本。新版本生效後取代較早登錄版本，包含舊的未來排程；故排了明日版本仍能立即更正。編輯使用最後登錄版本 UUID 防止覆蓋別台變更，摘要一律顯示目前生效版本。必須已有該病人的現役固定藥單才呈現暫停條件編輯器；僅選到目錄藥品不算。讀取或儲存失敗可在表單內重新讀取；重讀載入最新欄位及 UUID 並清空生效時間，要求人工核對後再儲存，不自動重試覆蓋他人版本。編輯介面提供「設為現在立即生效」操作：對時期間禁用輸入欄位並以序號防護競態，照護者若手動修改時間即刻取消未完成對時；送出時直接傳送 `'now'` 哨兵值，由 PostgreSQL `save_medication_hold_rule` 在同一交易內原子解析 `('now')::timestamptz`，完全消除第二次 RPC 網路往返延遲超過 1 分鐘回溯寬限期而被拒絕的風險；日期與不可回溯防線由資料庫權威時間統一驗證，資料庫特定錯誤（invalid time、changed、permission）由前端精確三語呈現，不以通用儲存失敗模糊原因。
- `medication_hold_day` 將醫囑日界與既有 04:00 `care_date` 分開。已確認 hold 以自己的起迄時間持續有效，後續血壓或規則修改不自動解除；換日後只查新日量測。
- 候選量測固定為該病人最新 `measured_at`；未來、過期、前日或未同步讀數不能略過改拿較舊值。確認提交完整 ID／數值／時間快照；DB 重新讀取比對。
- 條件尚未生效或已撤銷、且沒有有效 hold 時，context 的 `reading` 為空；一般按鈕只說「記錄已服用」，資料庫也強制不存血壓快照。過期或未來讀數不可冒充此次服用依據。
- 條件用藥頁以病人綁定的伺服器時鐘校正照護日；首次讀取日期不一致時先重讀，再呈現可操作卡片。正常 `taken` 必傳 `p_expected_care_date`，RPC 與實際服用照護日不符就拒絕並刷新父頁；請求跨過 04:00 也不會成功寫到另一日。照護日與同頁普通固定藥的正常服用時間及離線快照採「收到回應後」累計的伺服器估時計算，不把請求往返時間加成未來服用；這仍是可能落後網路延遲的估計值，不能保證離線時精確對時；請求與接收估計跨越照護日界時，普通藥按鍵只刷新、不寫入或排隊，待時間範圍明確再按。避免混合藥單寫到手機的錯誤日期；按下時已跨照護日就先換日，不送出舊日按鍵。歷史補記仍由 `actual_at` 決定，不受今日限制。
- `record_medication_hold_action` 原子寫事件與真實 intake。request UUID 保證回應遺失重試不重複寫；同劑仍受既有唯一鍵保護。hold/release 只操作整顆藥；release 必填新的依據，且不繞過仍符合的血壓條件。
- 無 `plan_id` 的舊 intake 也能走有原因的 `correction`：以原紀錄 patient／medication／時間留存不可變事件後移除錯誤事實，不補造藥單。直接更新／刪除仍禁止，非空 plan 必須仍是該病人藥品的固定藥單，新增 `taken` 的 plan 與 PRN 防線不放寬。
- 補記與更正另有原因、實際時間；包含已停用 plan、先前較多劑次及過去照護日。補記保留當時規則快照，沒有當時規則就留空，不借用今天血壓。更正移除目前 intake，但保留原事件與更正事件。補記結果按實際照護日與本機佇列對帳。
- 規則、血壓、plan、intake 共用一把 patient 級交易鎖；比為每顆藥設鎖簡單，跨藥品／血壓更新也有一致順序。資料庫驗證 plan／藥品／病人一致，既有規則的 plan 不可刪除、換藥或改為 PRN；可調劑量、停用或新增固定時段。目錄合併若要移轉這些 plan 會安全拒絕，須保留原身分或另行設計帶稽核的移轉。
- 新表 authenticated 只有 SELECT，RLS 每次依 `care_access.patient_id`＋`user_id` 判斷。只有受控 RPC 可寫；醫囑要求 `can_manage_medication`，決定／更正要求 `can_record`。操作者由 `auth.uid()` 取得。
- 有任何規則歷史（包含未來或已撤銷）的藥，直接 intake INSERT／UPDATE／DELETE 均需受控事件。這是刻意較嚴的舊版防線，避免舊快取繞過醫囑；無條件藥不受影響。條件用藥需要連線確認，離線事實保留待同步並可明確補記，不自動視為通過。

卡片、計數與刷新計時共用 `server_now` 加上送出請求後的單調經過時間（`performance.now()`）；不用可被手機設定改動的日曆時間判斷有效性，起點包含、終點不包含。保守計入整段往返時間，避免換日前產生、換日後才收到的回應延長舊暫停；延遲可能提前要求重新確認，但不會放行給藥。已暫停卡片只顯示事件的 `rule_snapshot`／`reading_snapshot`，讀數年齡相對決定時間 `created_at`，不拿後續複測或新醫囑替代。

補記與更正入口只列固定藥單（包含已停用版本）；RPC 無條件拒絕 PRN，原因與歷史時間都不能繞過。PRN 仍由既有獨立事件流程處理。

每分鐘、回到前景與醫囑換日刷新伺服器狀態及 intake；同日刷新保留表單草稿。病人切換立即移除上一人的卡片與草稿。服藥趨勢只計真實 intake，另列不可變事件；未回報觀察維持既有「病人連續整日零 intake」契約，任何真實 intake 仍中斷連續天數。hold 豁免必須保留 patient／medication 範圍：只有當日已建立的全部現役固定藥都被 hold 區間完整涵蓋才豁免；同藥相鄰區間可接續，其他藥、PRN 或未生效藥單不能補洞，不把 hold 轉為服用次數。沒有精確服藥鐘點時，部分日界覆蓋不能消除整日觀察。交接手冊與報告列出醫囑和生效資訊，不依紙本最後血壓產生給藥建議。

## Migration 與 rollout

`20261009233537_medication_daily_bp_hold.sql` 新增兩表、RPC、鎖與寫入防線；沒有真人門檻、資料回填或 production 操作。已有 intake 保留原樣。部署須先有資料庫契約再使用新畫面；缺表／RPC 會明確顯示讀取失敗。設定第一筆條件後，舊版 App 與舊離線佇列對該藥的未確認寫入會被拒絕，照護者改用新版的線上確認或補記事實。

回滾前端不能移除資料庫防線；已啟用條件的用藥仍須新版流程。不要刪除事件或回填假 intake 來讓舊版通過。staging 合併會依既有 GitHub Actions 套用 migration；正式發布另依 release policy 由使用者核准。本 PR 不合併、不觸碰 production。

## 排除的替代方案

- **只加備註**：沒有結構化比對與每劑暫停紀錄，依賴照護者每次重新讀懂。
- **遇到低血壓就永久停用 plan**：把當日暫停誤當成永久調藥，隔天無法自然回到原藥單。
- **只暫停一劑或同日新血壓正常就恢復**：違反使用者已明確補充的「今天不吃、明天重新確認」醫囑語意。
- **以血壓危險等級決定哪顆藥該停**：醫療判讀與特定藥品醫囑是兩個不同契約，不能互相推論。
- **將 held 塞入既有 intake 但不改讀取者**：近期趨勢、完成提示及舊 App 會把未吃當成已吃。
- **前端停用按鈕、沒有 DB 寫入防線**：今天頁、舊版、其他裝置、離線重送都可能繞過。
- **任意預設量測期限或所有藥套用 100**：系統自行補出的醫囑資訊可能改變實際照護行為。

## 畫面層次與可讀性優化（UI/UX Readability）

為解決看護與家屬於小螢幕或高解析度桌面檢視時「資訊淹沒、重要條件看不清」之問題，依 `ui-ux-pro-max` 與 `design-system/jia-jian-log/MASTER.md` 指引進行以下介面優化：

1. **資訊層級重構（MedicationHoldDose）**：
   - 依「15 秒原則」將最關鍵的「醫囑暫停條件、最新量測讀數、判定結論徽章、核心操作（確認暫停／記錄服用）」整合為高對比臨床判讀區塊，置於卡片核心。
   - 保留完整「服用方式」（`MedicationIntakeGuidance`），確保照護者在按下確認前能直接看見官方劑型指示（如不可磨粉、舌下含服）與家屬/藥師交代事項，不因過度精簡而遺漏操作指示。
   - 藥品名稱與規格享完整寬度，外觀特徵獨立成列並支援彈性換行，避免在 375px/390px 窄螢幕下遭多語長字串擠壓。
   - 條件比對徽章與確認暫停主按鈕全面採用 `amber-700`，對比度達 5.1:1（符合 WCAG AA 4.5:1 標準）。
   - 已確認暫停之量測讀數時間標示為「距確認時間 X 分鐘」，跨照護日未涵蓋警示維持 `text-sm font-semibold` 易讀字體大小。
   - 次要之「補記事實」、「更正紀錄」收納於卡片底部的可展開面板，不干擾常態服藥打卡。

2. **消除無樣式載入狀態與嚴格 Fail-closed**：
   - `MedicationHoldDose` 以 `plan.holdContext` 為初值平滑掛載，連線失敗時立即清空 context 恪守 fail-closed，杜絕在載入失敗或重試期間操作過期臨床按鈕。
   - `MedicationHoldFacts` 於讀取歷史計畫期間回傳 `null`，移除主畫面上浮動裸露的 `<p>載入中...</p>`。
   - `ModuleTrendSection` 與 `MedicationDoseHistoryPanel` 導入 `h-44` 固定高度之平滑載入骨架，杜絕趨勢圖載入時的版面突兀位移。

3. **觸控目標達標**：
   - 所有主要按鈕與表單欄位高度升級為 `min-h-12`／`min-h-11`，消除既有 7 個不達標觸控控制，通過 `touchTargetInventory.test.ts` 棘輪測試。
